Q1. What is a Thread?
Ans: 
- A thread is lightweight sub process that allows a java program to perform multiple tasks concurrently (multithreading).
- Multiple threads share the same memory space of a process but execute tasks independently.
- Threads are referred to as parts of a process that simply let a program execute efficiently with other parts or threads of the process at the same time. 
- Using threads, one can perform complicated tasks in the easiest way. 
- It is considered the simplest way to take advantage of multiple CPUs available in a machine. They share the common address space and are independent of each other. 
----------------------------------------------------------------------------------------------------
Q2. What is multithreding and usages of multithreading?
Ans: 
- Multithreading is a programming technique where multiple threads run concurrently within a single program to perform     different tasks at the same time. 
- It improves CPU utilization and performance.

There are various benefits of multithreading as given below:
1. Allow the program to run continuously even if a part of it is blocked. 
2. Improve performance as compared to traditional parallel programs that use multiple processes. 
3. Allows to write effective programs that utilize maximum CPU time
4. Improves the responsiveness of complex applications or programs. 
5. Increase use of CPU resources and reduce costs of maintenance. 
6. If an exception occurs in a single thread, it will not affect other threads as threads are independent. 
7. Less resource-intensive than executing multiple processes at the same time.

Q3. Ways to create a thread in Java?
Ans:
There are two ways to create thread in java.
1. Extending thread class
class DemoThread extends Thread {
    public void run() {
        System.out.println("Thread Running..");
    }
}

class MyThread {
    public static void main(String[] args) {
        DemoThread t = new DemoThread();
        t.start();
    }
}

2. Implementing Runnable
class DemoThread implements Runnable {
    public void run() {
        System.out.println("Thread running..");
    }
}

class MyThread {
    public static void main(String[] args) {
        Thread t = new Thread(new DemoThread());
        t.start();
    }
}

Why Runnable is better?
- Java supports single inheritance with classes.
- With Runnable we can achieve multiple inheritance.
- Allows better code separation
- Commonly used with Thread Pool & Executors

Q7. What is the start() and run() method of Thread class?
Ans:
Both methods belong to the Thread class, but they behave very differently.

start(): 
- Creates a new thread
- Invokes run() internally
- Runs code concurrently (multithreading)
- Can be called only once per thread object
- Executes run() in a separate thread
- JVM creates a new call stack
- Used for new thread
  
run():
- JVM does NOT create a new thread
- Code runs in main thread
- No concurrency
- Executes like a normal method call
- Used only to define thread logic
- No new call stack is created
- Used for defining thread logic

Why is calling run() manually dangerous?
Because calling run() executes on current thread, not a new one → causing:
- no concurrency
- unexpected race conditions
- breaking assumptions of multithreading
- hard-to-debug inconsistent behavior

Q8. What is Runnable and Callable Interface? Write the difference between them.
Both the interfaces are generally used to encapsulate tasks that are needed to be executed by another thread. 
But there are some differences between them as given below: 

Runnable Interface: 
This interface is basically available in Java right from the beginning. 
It is simply used to execute code on a concurrent thread.  

Callable Interface: 
This interface is basically a new one that was introduced as a part of the concurrency package. 
This is similar to Runnable but has two differences:
1. It returns value
2. It can throw checked exception
- It uses generics to define the return type of object.   

public interface Runnable  {   
  public abstract void run(); 
}  

public interface Callable<V>  {    
 V call() throws Exception;  
}

Differences:
Runnable Interface:It was introduced in JDK 1.0.	
Callable Interface: It was introduced in JDK 5.0, so one cannot use it before Java 5. 

Runnable Interface:	It simply belongs to Java.lang.
Callable Interface: It simply belongs to java.util.concurrent.

Runnable Interface: It does not return any result and therefore, cannot throw a checked exception. 
Callable Interface: It returns a result and therefore, can throw an exception.

Runnable Interface:	It uses the run() method to define a task.
Callable Interface: It uses the call() method to define a task. 

Example with Executors:
public class CallableExample {
    public static void main(String[] args) throws Exception {
        ExecutorService executor = Executors.newSingleThreadExecutor();
        Callable<Integer> task = () -> {
            Thread.sleep(1000);
            return 10 + 12;
        };
        Future<Integer> future = executor.submit(task);
        System.out.println("Result: " + future.get());
        executor.shutdown();
    }
}

With Runnable:
Runnable task = () -> {
    Thread.sleep(1000);
};

Future<?> future = executor.submit(task);
Object result = future.get(); // null

Ans: 
 run() method doesnt achieve concurrency then why run method is there?

    // thread job
}
This is the task body.

2. Reason 2: Runnable interface depends on run()

This is needed for thread pools, executors, etc.

You can reuse the same run() logic.

run it in a new thread

Java follows this design:
run() = what to do
start() = do it in a new thread
Simple, clean separation.

Q10. Common multithreading problems
Ans:
Deadlock: Threads wait for each other forever
Race Condition: Multiple threads modify data
Starvation: Thread never gets CPU
LivelockThreads active but not progressing

Problem1: Deadlock
- Deadlock occurs when two or more threads are waiting forever for each other to release resources.
- Each thread holds one lock and waits for another - nobody can proceed.
 
class DeadlockExample {
    static final Object lock1 = new Object();
    static final Object lock2 = new Object();
    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lock1) {
                System.out.println("Thread 1: Holding lock1");
                try { Thread.sleep(100); } catch (Exception e) {}
                synchronized (lock2) {
                    System.out.println("Thread 1: Holding lock2");
                }
            }
        });

        Thread t2 = new Thread(() -> {
            synchronized (lock2) {
                System.out.println("Thread 2: Holding lock2");
                try { Thread.sleep(100); } catch (Exception e) {}
                synchronized (lock1) {
                    System.out.println("Thread 2: Holding lock1");
                }
            }
        });

        t1.start();
        t2.start();
    }
}
Here: 
- Thread 1 holds lock1 and waits for lock2.
- Thread 2 holds lock2 and waits for lock1.
Condition for Deadlock(Coffman Condition)
All must be true:
1. Mutual Exclusion
2. Hold and wait
3. No preemption
4. Circular Wait

Fixes to Deadlock issue:
1. Acquire locks in same order and Use the same order everywhere
synchronized(lock1) {
    synchronized(lock2) {
        // safe code
    }
}

2. Use tryLock() (Advanced)
Use ReentrantLock with timeout. It Avoids infinite waiting.
if(lock1.tryLock(1, TimeUnit.SECONDS)) {
    if(lock2.tryLock(1, TimeUnit.SECONDS)) {
        // do work
    }
}

3. Avoid nested locks
Simplify design → fewer locks → fewer problems.
------------------
Problem 2: Race Condition
Occurs when multiple threads access shared data simultaneously and the final result depends on execution order.
Example: 
class Counter {
	int count = 0;
	void increament() {
		count++; //not thread safe
	}
}
Two threads may update count incorrectly - wrong result
Fixes: 
- Use synchronized
- Use Automic classes(AutomicInteger)

e.g.
synchronized void increament() {
	count++;
}
------------------
Problme 3: Starvation
A thread never gets CPU or resources because other threads keep taking them.
Example: 
- High priority threads always executes.
- Low priority threads never executes.
Fixes:
Fair scheduling(ReentraLock(true))
Avoid excessive thread priorities.
------------------
Problem 4: LiveLock 
Threads are not blocked but keep changing state in response to each other and make no progress.
Fixes:
- Add randomness or delay.
- Reduce over coordination between threads.
------------------
Problem 5: Memory consistency error
Changes made by one thread may not be visible to others
Example:
boolean flag = false;
//Thread 1
flag = true;

//Thread 2
while(!flag) {} //may loop forever
Fixes: 
Use volatile
Use synchronization
e.g.
volatile boolean flag = false;

Q11. Volatile keyword? 
Ans:
- The volatile keyword in java is used in multithreading to ensure visibility and ordering of variables of 
   variables across threads.
- Volatile tells JVM: "Always read this variable from main memory, not from a thread's local cache."
- volatile guarantees that when one thread updates a variable, all other threads immediately see the updated value.

Example without volatile:
class Shared {
	boolean flag = false;
}
Thread 1:
shared.flag = true;
Thread 2:
while(!shared.flag) {
	//may run forever
}

Problem: Thread 2 may never see the updated value.

With volatile
class Shared {
	volatile boolean flag = false;
}
Now:
- Change is immediately visible to threads
- Thread 2 will exit loop correctly.

Why volatile is needed?
- Java threads work with CPU caches, not directly with main memory.
- So without volatile, each thread may keep its own cached copy of a variable.
- One thread’s update may never be seen by others
- With volatile every update to variable go directly to main memory.
- And each thread reads volatile variable always from main memory
No stale values

volatile does NOT provide mutual exclusion
- Threads can still enter the same code at the same time
- No locking

Q12. Explain thread pool?
Ans: 
- Thread pools in Java (via ExecutorService) are a powerful way to manage multithreading efficiently.
- Instead of creating and destroying threads manually (which is expensive) a thread pool reuses a fixed number of threads 
  to execute multiple tasks.
- A Thread pool is a collection of pre-created worker threads that execute tasks from a queue.
- To create the thread pools, java.util.concurrent.Executors class usually provides factory methods.
Benefits: 
- Reduces overhead of thread creation.
- Improves performance
- Controls number of threads(avoids overload)
- Better resource management

How Thread Pool works 
1. Tasks are submitted
2. Tasks go into queue
3. Available thread picks a task
4. Executes it
5. Reuses thread for next task

Creating Thread Pools
1. Fixed Thread Pool
Example:
ExecutorService executor = Executors.newFixedThreadPool(3);
- In this only 3 threads will run tasks at a time

2. Cached Thread Pool
Example:
ExecutorService executor = Executors.newCachedThreadPool();
- Creates new threads as needed, reuses idle ones.

3. Single Thread Executor
Example:
ExecutorService executor = Executors.newSingleThreadExecutor();
- Ensures tasks run sequentially(one thread only)

4. Scheduled Thread Pool
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
- Used for delayed or periodic tasks.

- join() method is generally used to pause the execution of a current thread unless and until the specified thread 
  on which join is called is dead or completed. 
- To stop a thread from running until another thread gets ended, this method can be used.

Q15 What is Semaphore in multihreading??
- In Java, a Semaphore is a synchronization aid or concurrency utility used to control access to 
  a shared resource by limiting the number of threads that can access it at the same time.
- It is part of java.util.concurrent.
- Simply it ensures that Only a limited number of threads can access any resource at the a time.

A Semaphore maintains a set of permits:
- A thread must acquire() a permit before accessing the resource
- After finishing, it must release() the permit
- If no permits are available, the thread blocks until one becomes available

When to Use Semaphore
- Limit number of connections (DB, API, thread pool)
- Control concurrent access
- Producer–consumer problems
- Rate limiting
- Not ideal for simple mutual exclusion (use ReentrantLock instead)

Types of Semaphores
1. Counting Semaphore
- Has multiple permits
- Allows limited concurrent access
- Example: Only 3 threads allowed at once
Semaphore s = new Semaphore(3);

2. Binary Semaphore
- Only 1 permit
- Works similar to a mutex / lock
Example:
Semaphore s = new Semaphore(1);

Fair Vs UnFail Semaphore
Semaphore semaphore = new Semaphore(3, true); // Fair (FIFO)
Semaphore semaphore = new Semaphore(3, false); // Unfair (default)
Fair: Threads get permits in request order
Unfair: Better performance, no ordering guarantee

Common Semaphore Methods

1. acquire(): Acquires a permit (blocks if none available)
2. release(): Releases a permit
3. tryAcquire(): Tries to acquire without blocking
4. availablePermits(): Number of available permits
5. acquireUninterruptibly(): Acquires without responding to interrupts

Semaphore Example:
import java.util.concurrent.Semaphore;

class Worker extends Thread {
    private Semaphore semaphore;

    Worker(Semaphore semaphore) {
        this.semaphore = semaphore;
    }

    @Override
    public void run() {
        try {
            semaphore.acquire();
            System.out.println(Thread.currentThread().getName() + " acquired permit");
            Thread.sleep(2000); // simulate work
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            semaphore.release();
            System.out.println(Thread.currentThread().getName() + " released permit");
        }
    }
}
public class SemaphoreDemo {
    public static void main(String[] args) {
        Semaphore semaphore = new Semaphore(2);
        for (int i = 0; i < 5; i++) {
            new Worker(semaphore).start();
        }
    }
}

Q16. What is CountDownLatch in multithreading?
CountDownLatch is a synchronization utility from java.util.concurrent package 
that allows one or more threads to wait until a set of operations being performed in other threads completes.

What is CountDownLatch?
- It is initialized with a count
- Threads call countDown() to reduce the count
- Waiting threads call await()
- Once count becomes 0, all waiting threads are released
- One‑time use only (cannot be reset)

CountDownLatch is used when you want:
- One or more threads to wait until a number of tasks finish.
- A counter that counts down to zero.
- Once it reaches zero -> waiting threads are released
.
- Wait for multiple services to start
- Wait for multiple tasks to finish
- Parallel processing coordination
- Main thread waits until worker threads finish
- Not reusable → use CyclicBarrier or Phaser if reuse is needed


Creating a CountDownLatch
- import java.util.concurrent.CountDownLatch;
- CountDownLatch latch = new CountDownLatch(3);
- The count is 3

Common Methods
wait(): Waits until count reaches zero
await(long, TimeUnit): Waits with timeout
countDown(): Decrements the count
getCount():Returns current count


Countdown latch
import java.util.concurrent.CountDownLatch;

class Worker extends Thread {
    private CountDownLatch latch;
    Worker(CountDownLatch latch) {
        this.latch = latch;
    }
    public void run() {
        try {
            System.out.println(Thread.currentThread().getName() + " working");
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            e.printStackTrace();
        } finally {
            latch.countDown();
            System.out.println(Thread.currentThread().getName() + " finished");
        }
    }
}

public class CountDownLatchDemo {
    public static void main(String[] args) throws InterruptedException {
        CountDownLatch latch = new CountDownLatch(3);

        new Worker(latch).start();
        new Worker(latch).start();
        new Worker(latch).start();

        latch.await(); // main thread waits
        System.out.println("All workers finished. Main thread continues.");
    }
}
